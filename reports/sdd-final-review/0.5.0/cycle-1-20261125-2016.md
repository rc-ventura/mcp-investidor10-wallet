## Tech Leader Verdict

### Architecture Assessment
The 0.5.0 code change is small and fits the existing architecture.
- **ETF support.** `Etf` is added to `VALID_ASSET_TYPES` and `ASSET_TYPE_ALIASES`. `normalize_asset_type` does `strip().lower()` and an exact dict lookup. The endpoint path is built only from the canonical constant, so there is no path injection and no collision with `etfinternational`.
  - It reuses the existing pagination, validation, envelope and error code (ADR-0003, 0005, 0007).
  - The privacy mode is a field-based fail-closed allowlist, so `Etf` needed no special handling (ADR-0015).
  - The new docstring text sits in the `Args:` entry, which FastMCP serves as the parameter description. The usage rules before `Args:` are untouched, and `tests/contract/test_tool_descriptions.py` still guards that.
- **Release pipeline.**
  - The `verify` job now exports `UV_CACHE_DIR` next to `UV_PYTHON_INSTALL_DIR`.
  - All four action bumps are SHA-pinned at the stated versions, and permissions did not widen.
  - rc2 already ran the full chain on PyPI: build, publish, verify on 3 systems, and Promote (a no-op for an rc, as designed).
  - Between rc2 and HEAD only `__version__`, the plugin manifests and the changelog date changed. The artifact to be tagged is therefore functionally the one already exercised.
- **Dependencies.** The keyring chain (11 packages) is gone, and nothing in `src/` imports it. `pip-audit` is clean. Direct pins all meet the 7-day rule: fastmcp 4.2.0 is 12 days old, hatchling 1.33.0 and pytest 9.2.0 are 28 and 29 days old.
- **Complexity.** No new code paths, tools, error codes or dependencies. This is a low-risk release.
- **Transitive dependency age (the open question).** The technical fact derived by the coordinator was verified.
  - `plugin/.claude-plugin/plugin.json` launches `uvx --from mcp-investidor10-wallet==0.5.0 mcp-investidor10-wallet`.
  - `pyproject.toml` pins only `fastmcp==4.2.0`, `httpx==0.28.1` and `filelock==4.2.4`.
  - `uv.lock` is used only by `uv sync --locked` in `ci.yml` and `live.yml`, and by the `audit` export. The release `build` runs `uv build`, which does not use the lock.
  - So `authlib` and `uncalled-for` are resolved fresh by `uvx` on each end user's machine, to the newest compatible version, whatever the lock says. Re-locking would change CI and developer reproducibility only, and nothing end users receive.
- **Policy gap this exposes.**
  - The ADR-0001 transitive amendment ("oldest fixed version that respects the 7 days") was written for advisory-driven bumps and a lock-only scope. For a routine refresh with no advisory, "fixed" has no meaning. The `uv lock` that came with the fastmcp bump simply took the newest transitives.
  - It also shows that the ADR-0012 emenda ("what runs is exactly what was installed") holds for the top-level package only. Transitives float at install time.
  - Neither is a 0.5.0 defect, but the ADR-0001 amendment and a tech-debt record should capture the gap (items N1 and N2 below).

### ADR Compliance
- ❌ ADR-0001 Platform and storage choices: minor, policy-only violation of the transitive amendment. `authlib` 1.9.10 (uploaded 2026-11-20) and `uncalled-for` 0.6.2 (2026-11-19) are in `uv.lock` and are younger than 7 days.
  - Older eligible versions exist (authlib 1.9.5 to 1.9.9, uncalled-for 0.6.1).
  - No exception is recorded. The `virtualenv` exception does not apply, because it was justified by a red `audit` job and `pip-audit` is clean here.
