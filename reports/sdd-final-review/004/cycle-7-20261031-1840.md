## Tech Leader Verdict

### Architecture Assessment
- **Design.** The layers still match the ADRs. `WalletClient` is the only place that touches the source. The memory store, the server tools and the privacy allowlist keep their separate roles. `_redact` (`wallet_client.py:163-171`) is computed once as `shown` and used on every model-visible error path. That is the right shape: one choke point, no per-call patching.
- **`_redact` on raw text.** It is a regex on text with digit lookarounds. This is safe because the bootstrap enforces `[0-9]+`. The edge cases QA lists are harmless.
- **Gap in the depth guard.** `json.loads` accepts about 9,000 levels of nesting. The `except (ValueError, RecursionError)` at `:272` only covers the very deep case. A payload nested 256 to 9,000 levels passes `request()` and the `expected_type` check, and is cached. It then fails in pydantic serialization (`pydantic_core.to_json` on a 600-deep list raises `PydanticSerializationError`, "Circular reference detected"). `memory_store.py:72` (`_nests_deeper_than`) and `:256` already apply the correct guard to the other untrusted JSON source, but `wallet_client.py` does not use it. The two JSON entry points therefore apply the same rule differently.
- **Effect.** The model sees the masked generic error with `is_error` true but no `{error:{code}}` envelope. That breaks the ADR-0014 dual signal and leaves a poisoned cache entry. It is a contract defect, not a leak.
- **Threat boundary.** It needs a hostile upstream or a MITM, so ADR-0004 puts it out of scope. No wallet ID leaks through it.
- **`int(declared)` crash (`wallet_client.py:92-93`).** `isdigit()` followed by `int()` can raise a bare `ValueError`. Security refuted it over a real transport: h11 rejects those values first. It is mock-only, so it is cheap hardening and not a finding, and goes in the same 0.3.1 change as the depth guard.
- **Real-wallet-ID exposure.** This is the only item with irreversible consequences (see the Verdict and mandatory item 1).
  - The real wallet ID is tracked at `reports/sdd-final-review/004/cycle-5-20261029-0832.md:79`. The line is the "git grep ... 0 hits" verification claim, which quoted the very string it was proving absent.
  - Nothing in `.pre-commit-config.yaml` (ruff only) or in `ci.yml` checks for it.
  - `pyproject.toml` has no `sdist` target. Hatchling's default sdist includes every non-gitignored tracked file, and `release.yml:19` runs `uv build`, which builds the sdist. So tagging v0.3.0 would publish `reports/` with that ID to PyPI, and that cannot be undone. That is why this is a tag blocker and not just a documentation slip.
  - The Tech Leader did not build an sdist to confirm. The acceptance criterion in item 2 does that.
